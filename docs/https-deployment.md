# HTTPS staging and deployment preparation

The [Nginx template](../deploy/demo/https/nginx.conf.template) is a staging-first configuration, not permission to publish an installation. Its listener is explicitly IPv4 loopback. It does not request a certificate, install a service, open a firewall port, configure DNS, or change an existing deployment. Complete the application restrictions, storage/resource containment and expiry checks in [demo controls](demo-controls.md) before proposing public access.

## Isolate the rehearsal

Use a separate source checkout, application environment, workspace, socket namespace and test ports. Use synthetic data and a new test administrator. Never start the rehearsal server against an active workspace, reuse production credentials, or overwrite the running service's source/configuration. Existing viewer installations can be reused read-only; staging bridges, launch files, databases and outputs must remain separate.

A prepared OHIF distribution must contain the current MONAI Label extension, not merely an `index.html`. An older cached distribution can load images successfully while missing current visitor controls. Build from the pinned source and matching extension in a separate staging directory, then verify the countdown, expiry, manual-editing panel and annotation submission before selecting it with `MONAILABEL_OHIF_DIST`. Do not rebuild an in-use distribution in place.

Render the template into a private configuration file, replacing `__PUBLIC_HOST__` with one exact hostname, `__HTTPS_PORT__` and `__BACKEND_PORT__` with unused unprivileged test ports, and the two certificate placeholders with absolute paths to the certificate chain and private key. Quote paths if needed using Nginx configuration syntax; do not paste untrusted input into configuration. The hostname must be included in the certificate. Use the workspace's disposable local certificate only for local rehearsal, never as a publicly trusted certificate. Keep private keys out of source control, chat, logs and screenshots.

Run the backend on `127.0.0.1` with `--trusted-proxy 127.0.0.1`. Configure `MONAILABEL_ALLOWED_HOSTS` to the exact rehearsal hostname plus the required loopback names. The proxy replaces `X-Forwarded-For` and `X-Forwarded-Proto` and clears untrusted forwarding alternatives. Do not trust `*`, a whole client network, or a public peer. A different proxy architecture needs its own exact peer addresses and verification; this template assumes a single local edge and a private backend port. HTTP clients on the same host are inside that trust boundary.

Set `MONAILABEL_DESKTOP_BACKEND_URL` to the private backend origin, including its test port. Native viewers use their own session-authenticated Unix gateway; that gateway contacts the private backend directly and still receives normal application authorization. Do not route it through a public hostname or relax certificate checking.

For an invite-only rehearsal, keep `MONAILABEL_DEMO_SELF_REGISTER=0`, choose a conservative `MONAILABEL_DEMO_CAPACITY`, enable `MONAILABEL_DEMO_HTTP_LIMITS=1`, and enable the implemented lifecycle/cache-only/training-preview controls. Create the administrator and invitations through the private administrator path. The edge blocks bootstrap, legacy `/api/auth/register-demo`, account mutations, token minting, demo reset/audit administration, and interactive API documentation. It allows ordinary sign-in; it does not itself restrict sign-in to visitor accounts or replace application project authorization. Use separate visitor credentials, not an administrator account, for invited reviewers.

Open, automatically approved signup is a separate opt-in deployment choice described in [demo controls](demo-controls.md#automatically-approved-public-signup). `/api/auth/signup` is denied by the application unless all public-registration guards are enabled. The edge applies the same per-source bucket to signup and login. The read-only `/api/auth/accounts` directory is available only to authenticated administrators; it does not expose passwords or grant account-management privileges to visitors. Rehearse signup, capacity waiting, private starter projects and role restrictions before enabling this mode. Preparing the feature does not authorize turning an invite-only installation into an open demo.

The opt-in application ingress guard also covers the private backend and native gateway. It permits eight active HTTP handlers and sixteen WebSocket connections, with up to sixteen additional HTTP requests waiting at most five seconds for a handler slot. Waiting requests do not consume application upload spools; the finite queue accommodates parallel viewer modules without raising active handler capacity. It bounds each HTTP body to 128 MiB (16 KiB under `/api/auth/`), and imposes a thirty-second total body-receive deadline. It validates both declared and streamed sizes before dispatch; small bodies stay in memory and larger bodies spool to automatically closed temporary files. Authenticated endpoints share account-level buckets across cookies and bearer sessions: five writes/second with a burst of sixty, and thirty GET/HEAD requests/second with a burst of 256. The separate read burst supports authenticated viewer modules without spending the write allowance. Rejected requests do not extend a lockout; another account has its own buckets. Full or timed-out request queues return `429` with `Retry-After`. This bounds ingress staging and request rates, not JSON expansion, durable workspace storage, or fair GPU scheduling. Long-lived HTTP streams occupy request slots; include multi-tab viewer usage in capacity testing.

The supplied launcher uses the `wsproto` transport with a 16 MiB WebSocket message limit and compression disabled, and limits Uvicorn concurrency to 64 when the ingress guard is enabled. The server package requires the tested Uvicorn 0.53 baseline or newer because older transports did not all enforce message-size limits. Deploy through this launcher, or explicitly reproduce and verify these settings in a custom ASGI runner; middleware cannot stop a transport from buffering oversized frames before dispatch. The HTTPS rehearsal checks a fragmented oversized message receives close code `1009` without reaching application handling.

The edge supports TLS 1.2/1.3, rejects unknown TLS/HTTP hostnames, forwards WebSocket upgrades, streams responses without disk buffering, and does not retry mutating upstream requests. It sets a one-hour HSTS policy without `includeSubDomains` or preload. It limits bodies to 128 MiB, source request rates to 20/second (burst 256 for viewer startup), writes to five/second (burst 40), sign-in to six/minute (burst six), and concurrent requests to 16 per source and 64 overall. Edge overload returns `429` and `Retry-After`; application limits remain separate. Shared-NAT users share edge source limits, so measure the intended invited group before changing them. These are finite limits, not protection against a volumetric denial-of-service attack.

Use a non-root proxy process, a read-only root filesystem, dropped capabilities, `no-new-privileges`, bounded CPU/memory/PIDs, and a small bounded `/tmp`. All proxy temporary paths are under `/tmp`. Request/access logging is disabled here to avoid recording sensitive URLs; do not enable arbitrary-body/header or query-string logging. Any future operational logging needs rotation, redaction and retention review.

## Validation before any cutover

The disposable `tests/e2e/test_https_edge.py` test uses an already installed Nginx image, a temporary certificate/account, random localhost-only ports and a separate workspace. It performs `nginx -t` and checks certificate trust, wrong-host rejection, the private-only endpoints, Secure/HttpOnly/SameSite cookies, same-origin writes, streamed binary responses, WebSocket upgrade/frames, forwarded-header spoofing, oversized bodies and login throttling. It removes only its own randomly named container. It does not contact a certificate authority or test internet routing.

With a cached image and the existing development/E2E dependencies, run:

```bash
MONAILABEL_TEST_NGINX_IMAGE=nginx:1.28-alpine uv run pytest --desktop-e2e tests/e2e/test_https_edge.py
```

Select and verify an approved supported image before a real deployment; the test tag above is not a promise about future security updates. The test container uses host networking solely to reach the loopback test backend; its configuration binds only loopback and mounts only its test configuration/certificates read-only. Native desktop containers remain networkless.

With the native E2E prerequisites already prepared, set `MONAILABEL_TEST_HTTPS_EDGE=1` and `MONAILABEL_TEST_NGINX_IMAGE` when running `tests/e2e/test_browser_desktop.py::test_browser_native_viewer` with `--desktop-e2e`. This sends the browser through the same HTTPS template while native viewers use their private gateway. Chromium trusts only that rehearsal's temporary certificate public key; no machine trust store is changed. Explicit `MONAILABEL_TEST_DESKTOP_IMAGE` and `MONAILABEL_TEST_NOVNC_DIR` select already-installed viewer assets without a build/download. This offline overlay route tests the staged bridge/entrypoint against the selected cached base image; it does not prove a clean production image build from scratch.

Add `MONAILABEL_TEST_DEMO_VISITOR=1` for the native workflow check to prepare synthetic data as the test host and then sign in as a non-administrator invited visitor. Both the browser and native gateway use that visitor's credentials. This variant verifies that the visitor policy retains existing annotation display, draft input, clipboard, resizing and reconnection behavior without granting upload or provider-management capabilities.

Also verify an invited account's first-login capacity check with signup disabled, two distinct visitors' authorization boundaries, expiry during active work, queue saturation, no paid provider requests, the actual prepared dataset/model catalog, storage exhaustion behavior, and both native-viewer/browser workflows. Run the ordinary lint, format, typing and regression commands in `AGENTS.md`. A successful TLS test does not establish all these application properties.

## Operator-only deployment decisions

Before changing an existing installation, obtain explicit approval for public exposure, certificate issuance/renewal, service installation, any administrator-level filesystem/host containment work, and routing/firewall/DNS changes. Confirm ownership of the intended hostname and its certificate; use a supported free certificate workflow if appropriate, without sharing DNS/account credentials in chat. Public IPv4 and IPv6 policy, NAT and upstream-router behavior need independent checks from outside the network. Do not infer internet reachability from a loopback test or disable management protection to make a test pass.

Take and verify a recoverable backup during an agreed maintenance window. Preserve the previous service configuration and source/environment version. Save/submit native drafts and explicitly end older pre-isolation desktops before moving users to the new runtime; never silently kill sessions to complete a deployment. Establish an approved durable storage quota/retention plan for native writable mounts as well as application data. Changing those mounts to volatile storage without an explicit draft-preservation design is not an acceptable substitute.

The [cold workspace backup and restore helper](demo-backups.md) refuses an active backend and never overwrites a restore destination. It covers workspace files, not external viewer volumes or deployment/firewall configuration. Rehearse it with disposable data, then separately preserve the remaining configuration and verify the final off-machine copy.

Include provider/decoder scratch, temporary-spool reservations, SQLite overhead, external CVAT data and service logs in that host disk plan. The application's checked export and inference input/result spools do not reserve physical filesystem blocks or bound arbitrary provider files. Rehearse low-space behavior with disposable data, including a retained reservation after a worker crash; recover only confirmed orphaned operation directories after their processes have ended. Application quota exhaustion must not be worked around by clearing accounting or deleting saved user work.

The optional [bounded storage preparation helper](demo-storage.md) creates a new persistent filesystem without moving live data. It does not complete the separate application-path migration or protect writes outside that filesystem.

Only after all gates pass should an operator adapt the loopback listener and network boundary for the chosen public topology. Keep the backend, SSH, model coordinator, Docker daemon and administration path private. Perform a small invited trial and verify failures deny access without disrupting another visitor or the private administrator path. No cutover is automated by this package.

## Rollback

During rehearsal, stop only the separate staging edge/backend and their named disposable viewer containers. Confirm the pre-existing demo still responds and no staging listener remains. Retain test logs/screenshots needed for review; delete only positively identified disposable data after review.

After a separately approved public cutover, first stop new admission and remove the new public entry path using the operator's recorded firewall/proxy rollback procedure. Preserve logs and visitor work for diagnosis. Restore the previous reviewed service/source/environment configuration while ensuring only one server owns each workspace. Do not run old and new backends simultaneously against the same database, erase annotations to resolve a failure, or restore a backup over newer work without explicit reconciliation approval. Recheck the private administrator path and ordinary demo health before announcing recovery.
