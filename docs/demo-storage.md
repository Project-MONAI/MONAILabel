# Bounded demo storage preparation

`scripts/demo_storage.py` prepares a new 128 GiB, file-backed ext4 filesystem for the dedicated Linux `demo` account (UID/GID 1001). It requires administrator approval, installed systemd/util-linux/e2fsprogs tools, and at least 160 GiB free on the underlying filesystem. Running it without `--apply` prints a plan and makes no changes.

After reviewing the script, an administrator copies it to `/root/monailabel-demo-storage.py` with root ownership and mode `0700`, then runs that protected copy with `sudo /usr/bin/python3 -I /root/monailabel-demo-storage.py --apply`. The helper never imports code from the service account. Do not run it from a service-user-writable directory as root.

The helper refuses existing targets, links, mismatched account IDs, writable parent directories and insufficient free space. It creates only a new regular image file at `/var/lib/monailabel-demo-storage/demo-data.ext4`; it never formats a partition or existing image. The backing file remains root-owned, mode `0600`. It mounts that image at `/var/lib/monailabel-demo-storage/data`, verifies the filesystem/capacity, and prepares private `workspace`, `tmp`, `native-sockets` and `logs` directories for `demo`. A dedicated mount unit enables the filesystem at boot. The underlying unmounted directory remains root-only to prevent silent fallback writes. Initial allocation reserves space; filesystem metadata consumes some of the nominal capacity. Unrelated host writers or administrator trimming remain outside this reservation.

This preparation does not stop/restart the application, copy existing work, install packages, alter `/etc/fstab`, or change certificates, firewall rules or DNS. On failure it leaves partial state for inspection and refuses a blind rerun. Do not delete or reformat those files to bypass a refusal. After application migration, this filesystem may contain the only current copy of annotations and drafts; removing it is destructive.

Creating the filesystem alone does not constrain the running demo. A separate reviewed cutover must preserve a verified backup, copy data while every writer is stopped, point the application and provider scratch/native writable paths at the mount, and fail closed when it is unavailable. Verify those paths and low-space handling before public access. Downloads/model caches, Docker writable layers/logs, external CVAT volumes and writes elsewhere are not bounded by this filesystem. Retain separate container limits and log rotation; this is not an operating-system sandbox or per-visitor filesystem quota. Keep durable drafts on persistent storage and never remove saved work to recover quota.

## Guarded application startup

`scripts/demo_storage_run.py` wraps the existing application command without changing its package versions. Run it as the dedicated application account, after the ordinary demo environment launcher has set cache/tool paths. Supply `--storage` with the mounted filesystem, `--workspace` with the migrated workspace under its private `workspace` directory, and `--socket-dir` with a short alias resolving to its `native-sockets` directory. Use `--check-only` first; otherwise place the unchanged application command after `--`.

The wrapper refuses an absent mount, unexpected capacity, unprotected directories, missing database/key files, an outside workspace or an incorrect/overlong socket alias. It does not create a workspace, migrate files, alter credentials, stop services, or provision tools. It sets the workspace, standard temporary-directory variables and native socket location only, then replaces itself with the application process. A stopped or missing mount therefore fails closed on startup; the underlying root-only mountpoint also prevents fallback writes. Never unmount storage beneath a running application.

Keep the socket alias short because the namespace and session suffix must fit Linux's Unix-socket path limit. The alias must resolve to the persistent bounded filesystem, not a volatile directory. The wrapper preserves all other launcher settings, including existing cache/tool locations. A private storage-only migration is not a deployment of pending application security fixes or authorization for public exposure.

For cutover, stop all writers in an approved maintenance window, make a fresh cold backup, restore into a new private workspace directory on the mounted filesystem, and verify the manifest, database integrity, credential key and annotation records before restarting. Preserve the old workspace and service configuration. Restart only one backend; confirm the selected data/temporary paths and original application version. If validation fails before accepting new work, stop that backend and restore only the service configuration to use the untouched original workspace. Never roll an older copy over newly saved work.
